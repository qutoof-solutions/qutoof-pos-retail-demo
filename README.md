# قطوف سي آر إم | Qutoof CRM

منصة عمليات SaaS متعددة المستأجرين تدعم العيادات والتجميل والرياضة والاستشارات. يحتوي المستودع على أساس المصادقة والبيانات، ووحدات التشغيل الأساسية للمرحلة الثانية: التقويم، الفروع والخدمات، الجداول، ملفات العملاء والسجل الطبي، الانتظار، نقطة البيع وتقفيل الوردية.

## المتطلبات

- Node.js 20 أو أحدث وnpm.
- حساب Cloudflare لإنشاء D1 وKV وR2 قبل النشر.
- GitHub Actions لفحوص CI بعد الدفع.

## الإعداد المحلي

```bash
npm ci
cp .dev.vars.example .dev.vars
```

ضع قيمة عشوائية قوية لا تقل عن 32 محرفاً في `SESSION_SECRET` داخل `.dev.vars`، ولا ترفع هذا الملف إلى Git. لإعداد Cloudflare، أنشئ الموارد ثم حدّث معرّف D1 وKV في `wrangler.toml`:

```bash
npx wrangler d1 create qutoof-db
npx wrangler kv namespace create KV_BINDING
npx wrangler r2 bucket create qutoof-crm-files
```

اربط معرّفات D1 وKV الصادرة من حساب Cloudflare في `wrangler.toml`، مع إبقاء أسماء الربط `DB` و`KV_BINDING` كما هي لأنها مستخدمة في التطبيق. لا ينشئ المستودع موارد Cloudflare ولا ينشرها تلقائياً.

## التشغيل والبناء

```bash
npm run dev
npm run typecheck
npm test
npm run test:integration
npm run lint
npm run build
npm run pages:build
```

`npm run pages:build` يشغّل محول Cloudflare Pages وينشئ `.vercel/output/static`. لمعاينة Pages محلياً:

```bash
npm run preview
```

## قاعدة البيانات والترحيلات

مخطط Drizzle موجود في `lib/db/schema.ts`، وترحيلات D1 في `drizzle/migrations/`.

```bash
npm run db:generate
npm run db:migrate:local
```

بعد مراجعة الترحيلات وتكوين معرّفات موارد الإنتاج وأسرارها:

```bash
npm run db:migrate:remote
npm run deploy
```

ترحيلات المرحلة الثانية تضيف تفاصيل بنود الفواتير ومدفوعاتها، أرصدة باقات الجلسات واستهلاكها، وقيود قاعدة البيانات اللازمة لمنع التداخل المتزامن في المواعيد، وتكرار دور الموعد، والورديات المفتوحة المتعددة للفرع. تُحدّث جداول الأرصدة بواسطة SQLite triggers داخل D1 لضمان استهلاك الجلسة مرة واحدة فقط.

## وحدات المرحلة الثانية

- **التقويم:** عرض يومي وأسبوعي، إنشاء المواعيد وتعديلها، وعرض الحالات بألوان واضحة. تمنع طبقة D1 تداخل مواعيد مقدم الخدمة، ويتحقق API من الجداول والاستراحات وإغلاقات الطوارئ والمنطقة الزمنية.
- **الفروع والخدمات:** إدارة الفروع وكتالوج الخدمات والباقات والأسعار والمدد وعمولات مقدمي الخدمات وعدد جلسات الباقة.
- **الجداول:** ساعات عمل أسبوعية حسب الفرع ومقدم الخدمة وفترات الراحة، مع استثناءات وإغلاقات طارئة.
- **ملف العميل والسجل:** بحث بالاسم أو الهاتف، سجل الزيارات، الملاحظات والوصفات والمتابعات، مرفقات خاصة محفوظة في R2، والفواتير والمدفوعات وأرصدة الجلسات وفق الدور.
- **الانتظار:** إصدار الدور للموعد، النداء وبدء الخدمة وإنهاؤها، وشاشة TV مستقلة على `/queue/[branchId]` لا تعرض أسماء العملاء أو معلومات تعريفية.
- **نقطة البيع والورديات:** فاتورة محسوبة من أسعار D1، دعم أكثر من وسيلة دفع في الفاتورة، حفظ سجل التحصيل، واحتساب رصيد النقد المتوقع وفارق المطابقة عند الإغلاق.
- **أوراق القبض والدفع:** تسجيل شيكات العملاء وتخصيصها اختيارياً لفاتورة، وحجز المتاح دون تسجيل إيراد قبل التحصيل؛ وتسجيل شيكات الموردين المرتبطة بفاتورة شراء وحجز رصيدها حتى الصرف. عند ارتداد شيك عميل محصل، يُعكس قيد الدفعة مع توثيق غير قابل للمحو، ويُعاد رصيد الفاتورة وتُسجل تسوية سالبة على الوردية المغلقة ذات الصلة. لا تُطبق migration الشيكات على D1 الإنتاجية ضمن هذا التغيير.

تسجيل طريقة الدفع الإلكتروني هنا هو حفظ محاسبي لطريقة التحصيل ومرجعها، وليس تكاملاً مع بوابة دفع أو معالجة بطاقات.

## المصادقة والصلاحيات

- كلمات المرور محفوظة بصيغة PBKDF2-HMAC-SHA256 مع salt عشوائي و10,000 دورة، لتقليل استهلاك CPU في Cloudflare Pages. هذا أقل مقاومةً للتخمين خارج النظام من إعداد 310,000 دورة؛ استخدم كلمات مرور طويلة وفريدة. يمكن زيادة الجولات بعد رفع حد CPU والتحقق من زمن التنفيذ.
- جلسات JWT موقّعة باستخدام Web Crypto و`jose`، بملف Cookie من نوع `HttpOnly` و`SameSite=Lax` و`Secure` على HTTPS؛ ويُستخدم KV لإبطال الجلسة عند الخروج.
- حساب المدير الأول ينشأ عبر التسجيل العام. حسابات `Super Admin` تُنشأ إدارياً فقط.
- تتطلب واجهات العمليات جلسة نشطة، وتعيد التحقق من المستخدم والدور والمستأجر وحالة الحساب. لا يُقبل `tenant_id` من المتصفح؛ تُستخرج هوية المستأجر من الجلسة الموقعة.
- صلاحيات العرض والكتابة مقسمة بين `business_admin` و`reception` و`provider`. بيانات EHR والمدفوعات والشاشة العامة لها قواعد عرض مستقلة.

## عزل بيانات المستأجر

يحمل كل جدول تشغيلي `tenant_id` وفهرساً يبدأ به. تستخدم عمليات القراءة والكتابة معرف المستأجر المحفوظ في الجلسة، وتتحقق من ملكية الفروع والخدمات والعملاء والمواعيد والملفات قبل الربط بها. المرفقات في R2 مفاتيحها ضمن مساحة المستأجر، وتنزيلها يتطلب مصادقة وتحققاً من ملكية سجل D1.

## أسرار الإنتاج

اضبط `SESSION_SECRET` في Cloudflare Workers/Pages Secrets، ولا تضفه إلى `[vars]` أو Git:

```bash
npx wrangler pages secret put SESSION_SECRET
```

تضيف المرحلة الثالثة بوابة الحجز العامة وPWA ومحرك WhatsApp Cloud API والعمولات وسحب المواعيد وإفلاتها. تضيف المرحلة الرابعة لوحة Super Admin، والفوترة اليدوية عبر تحويل وإيصال Telegram، وتجارباً واشتراكات وقيود إتاحة وميزة impersonation مع تدقيق. دفع العملاء داخل المنشأة يظل منفصلاً عن اشتراك SaaS، ولا يُعالج النظام مدفوعات بطاقات أو تحويلات آلياً.

## توافق Cloudflare

يستخدم المشروع Next.js `15.5.27` مع `@cloudflare/next-on-pages` المطلوب. محول `next-on-pages` معلّم من ناشره بأنه متروك ويعلن سقف peer dependency أقدم؛ يتجاوز `.npmrc` هذا القيد القديم مع الإبقاء على إصدار Next المصحح أمنياً. تم اختبار بناء Pages محلياً. إذا توقف المحول عن مواكبة Next في تحديث لاحق، ينبغي الانتقال هندسياً إلى OpenNext بدلاً من الرجوع إلى إصدار متأثر أمنياً.


## وحدات المرحلة الثالثة

- **بوابة الحجز العامة:** `/{slug}` تعرض صفحة المنشأة وخدماتها ومقدميها، وتستخرج المواعيد المتاحة في نطاق 90 يوماً وفق المنطقة الزمنية وجداول العمل والاستراحات والاستثناءات وحجوزات D1 القائمة. إنشاء الموعد يعيد فحص التوفر على الخادم ويعتمد على trigger D1 الذي يمنع تداخل حجوزات مقدم الخدمة عند التزامن. تحفظ تفضيلات الدفع: نقداً عند الحضور أو طلب الدفع الإلكتروني؛ لا يُعالج أي مبلغ إلكترونياً.
- **بطاقة الحجز:** `/{slug}/booking/{code}` تعرض تفاصيل الموعد وQR يُنشأ محلياً في المتصفح ورابط Google Calendar. رابط الإدارة يحمل رمزاً عشوائياً منفصلاً لا يُخزّن إلا hash منه؛ يستطيع العميل الذي يملك الرابط إلغاء الموعد أو إعادة جدولته حتى ساعتين قبل بدايته. لا تتضمن شاشة الانتظار العامة معلومات شخصية.
- **PWA:** لكل منشأة manifest ديناميكي عند `/{slug}/manifest.webmanifest` ليبدأ التطبيق المثبت على صفحة الحجز الخاصة بها. يخزن Service Worker الملفات الثابتة فقط؛ لا يخزن APIs أو بيانات المرضى أو لوحة المستأجر أو الحجوزات. لا تعمل عمليات الحجز دون اتصال، حفاظاً على سلامة التوفر والخصوصية.
- **WhatsApp:** `services/whatsapp.ts` يضع رسائل التأكيد والتذكير والتقييم في صندوق إرسال idempotent مع محاولات محدودة وإعادة محاولة متباعدة. لا تُرسل الرسائل إلا عند موافقة العميل الصريحة. يخزن access token بعد AES-GCM ولا يعيده إلى الواجهة. webhook Meta عند `/api/webhooks/whatsapp` يتحقق من GET challenge وHMAC-SHA256، ويمنع معالجة event المكرر، ويعالج تأكيد العميل أو طلب إعادة الجدولة. endpoint التصريف الداخلي يحتاج `WHATSAPP_CRON_SECRET` مستقلّاً.
- **القوالب:** قوالب Meta يجب أن تكون منشأة ومعتمدة في حساب WhatsApp Business قبل الإرسال. اضبط الأسماء واللغة في شاشة `/dashboard/whatsapp`. قالب confirmation/reminder يستقبل متغيرات النص بالترتيب: اسم العميل، الخدمة، التاريخ، الوقت، الفرع/المنشأة، رابط البطاقة. قالب reminder يحتاج زري Quick Reply بترتيب: `confirm:{booking-code}` ثم `reschedule:{booking-code}`. قالب review يستقبل اسم العميل، الخدمة، رابط تقييم Google Maps. تأكد أن القوالب المعتمدة تطابق هذه المتغيرات والأزرار حرفياً.
- **التذكيرات:** Cloudflare Worker مستقل عن Pages يستدعي endpoint داخلياً كل خمس دقائق (`workers/whatsapp-cron.ts`). هذا يعني أن تذكير 24 ساعة له دقة جدولة تصل إلى دورة Cron؛ أما رسالة التأكيد فتحاول الإرسال مباشرة بعد إنشاء الموعد. لا يعتمد التشغيل على خدمة أتمتة داخلية أو عملية خادم دائمة.
- **العمولات:** `/dashboard/commissions` و`/api/ops/commissions` يعرضان العمولات من بنود فواتير المستأجر المدفوعة، وفق نسبة العمولة المحفوظة وقت إنشاء الفاتورة، ويصنفانها بتاريخ التحصيل `invoices.paid_at`. migration `0005` يضيف تاريخ السداد ويملأه للفواتير المدفوعة الموجودة بتاريخ `updated_at`.
- **التقويم:** يمكن سحب بطاقة الموعد إلى وقت/يوم آخر على شبكة نصف ساعة؛ تغيير مقدم الخدمة يظل خاضعاً لتأكيد API وفحوص التوفر والصلاحيات وقيود D1. لا يكفي تغيير الواجهة وحده لإقرار النقل.

## تهيئة WhatsApp والنشر

لا تُرفع أسرار Meta أو قيم التشغيل المحلية إلى Git. أنشئ/تحقق من Meta App وWhatsApp Business Phone Number وaccess token الدائم، واعتمد القوالب المطلوبة، ثم اضبط القيم في Cloudflare Pages (Production وPreview عند الحاجة):

- `WHATSAPP_APP_SECRET`: سر Meta App للتحقق من `X-Hub-Signature-256`.
- `WHATSAPP_VERIFY_TOKEN`: قيمة عشوائية تختارها لاختبار webhook handshake.
- `WHATSAPP_ENCRYPTION_KEY`: سر عشوائي قوي لا يقل عن 32 محرفاً؛ يجب الحفاظ عليه ثابتاً بعد ربط الحساب، وإلا يتعذر فك access tokens المحفوظة.
- `WHATSAPP_CRON_SECRET`: قيمة عشوائية قوية لا تقل عن 32 محرفاً، وتُسجل أيضاً كـ Worker Secret بالقيمة نفسها.
- `NEXT_PUBLIC_BASE_URL`: عنوان HTTPS النهائي للتطبيق؛ تضبط كـ Pages runtime variable كي تتضمن رسائل العميل روابط بطاقات صحيحة.

اضبط `WHATSAPP_APP_SECRET` و`WHATSAPP_VERIFY_TOKEN` و`WHATSAPP_ENCRYPTION_KEY` و`WHATSAPP_CRON_SECRET` كـ Pages Secrets في Cloudflare Dashboard أو عبر `wrangler pages secret put <NAME> --project-name qutoof-crm-2`. عيّن callback في Meta إلى `https://<domain>/api/webhooks/whatsapp` واستخدم `WHATSAPP_VERIFY_TOKEN` نفسه. لا تُرسل قيمة التوكن في محادثة أو مستودع.

لتهيئة Worker المجدول:

1. انشر تطبيق Pages واضبط موارد D1 وKV وR2 الحقيقية في `wrangler.toml`، بدلاً من المعرفات المحلية الأولية.
2. نفّذ `npm run db:migrate:remote` بعد مراجعة migrations والنسخ الاحتياطي لقاعدة الإنتاج.
3. اضبط `APP_BASE_URL` كـ Worker variable على عنوان HTTPS المنشور، و`WHATSAPP_CRON_SECRET` كـ Worker Secret بالقيمة المطابقة لسر Pages.
4. نفّذ `npm run cron:deploy` لنشر Worker وتفعيل Cron كل خمس دقائق. التطوير المحلي: `npm run cron:dev` مع قيم `.dev.vars` مناسبة.
5. في Meta، اضبط subscriptions لأحداث `messages` على التطبيق، واستخدم صفحة إعداد WhatsApp لمعلومات `phone_number_id` وtemplate names واللغة. اختبر باستخدام رقم تجريبي وموافقة WhatsApp فعلية قبل التشغيل العام.

لا يرفع commit أي أسرار، ولا ينشئ موارد Cloudflare أو تطبيق Meta أو يرسل رسالة حقيقية تلقائياً. يلزم تنفيذ إعدادات هذه الخدمات ونشر Pages/Worker في حساب المالك قبل إتاحة الخدمة للعامة.

تتطلب لوحة Phase 4 أيضاً تهيئة Telegram وبذر أول حساب `super_admin` بسر bootstrap لمرة واحدة. راجع [دليل تشغيل الفوترة ولوحة المنصة](PHASE4_OPERATIONS.md) للأسرار وتهيئة webhook وترتيب الترحيل والنشر.


## تدقيق سلسلة التوريد

في التحقق المحلي للمرحلة الثالثة: `npm audit --omit=dev` لم يجد ثغرات في تبعيات التشغيل. الفحص الكامل لـ npm أبلغ عن 16 نتيجة ضمن أدوات التطوير/البناء (10 عالية، 5 متوسطة، 1 منخفضة)، ومن بينها حزمة `@cloudflare/next-on-pages` التي يصنفها npm مهجورة ويوصي بمحول OpenNext. لم تُحدّث بنية الاستضافة في هذه المرحلة حفاظاً على إعداد Cloudflare Pages الحالي؛ لذلك يلزم تقييم ترقية محول النشر وأدوات البناء قبل اعتماد نشر إنتاج عام، رغم نجاح build وPages adapter.
