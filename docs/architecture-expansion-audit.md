# التدقيق المعماري لخطة توسعة قطوف CRM

**تاريخ التحديث:** 2026-10-10
**قاعدة العمل:** `c20d126`، وهو الأساس المشترك لـ`main` و`feature/rbac-universal-inventory` عند بدء المرحلة.
**النطاق الحالي:** تنفيذ RBAC وUniversal Inventory & Suppliers على فرع الميزة، مع اختبارات محلية اصطناعية فقط. لم تُطبّق migrations `0012–0015` على D1 الإنتاجية ولم يُنشر هذا العمل.

## الخلاصة التنفيذية

التطبيق Next.js 15 متعدد المستأجرين ويستخدم Cloudflare Pages وD1 وKV وR2 وDrizzle. أُنجزت على فرع الميزة مصفوفة أدوار مركزية وإدارة فريق محدودة، إضافة إلى دورة مخزون وموردين ومشتريات وحركات وPOS وربط استهلاك المواد بالخدمات. بقيت الأدوار التاريخية كما هي، وأضيفت الأدوار الجديدة بصورة additive. آخر migration مضافة لهذه المرحلة هي `0015`.

التحقق المكتمل يشمل فحوص الأنواع والوحدة والتكامل وlint وبناء Next.js وPages واختبارات HTTP على Pages/D1 محليتين ببيانات اصطناعية. هذه التغطية الموسعة **ليست** مراجعة أمنية شاملة لكل endpoint/method، وليست اختبار قبول على Preview منفصل أو على الإنتاج. لا نشر ولا ترقية إنتاجية ضمن هذه الخطوة.

## سلامة المخزون والخصوصية

1. جميع عمليات المخزون والموردين محكومة بنطاق المستأجر، وD1 تنفذ معاملات الشراء والحركة وبيع POS واستهلاك المواد ذريًا مع مفاتيح عدم تكرار حيث يلزم.
2. لا يُسمح بالمخزون السالب افتراضيًا. تُحفظ الحركات كسجل تدقيق، وتُخصم مواد الخدمة عند إكمال الموعد/تذكرة Queue ضمن معاملة واحدة وبطريقة تمنع الخصم المكرر.
3. صرف الدفعات يستخدم FEFO للدفعات غير المنتهية، ثم FIFO حسب وقت الاستلام عند التساوي؛ تُرفض زيادة الرصيد في تشغيلة منتهية.
4. بيانات المرضى والمرفقات حساسة. يلزم استكمال مصفوفة مراجعة الوصول للملفات والسجل السريري على كل route/method قبل أي ادعاء بمراجعة أمنية شاملة.
5. لا حذف آلي لبيانات طبية أو مالية، ولا سياسة احتفاظ افتراضية غير معتمدة.
6. لا تغييرات D1 إنتاجية ولا نشر إنتاجي قبل مراجعة migrations واختبار staging منفصل وإجراء مراجعة/دمج صريح.

## نتائج التحقق على الفرع

- `npm run typecheck` — ناجح.
- `npm test` — ناجح، **46/46**.
- `npm run test:integration` — ناجح؛ SQLite تكامل يغطي **16 migration**.
- `npm run test:inventory` — ناجح؛ migrations `0000–0015`، بما فيها حدود الرصيد والدفعات وidempotency.
- `npm run test:api` — ناجح على Pages وD1 محليتين وبيانات اصطناعية: عزل مختار بين مستأجرين، حواجز أدوار، شراء/سداد مورد، تعارض تشغيلة متزامن، رفض تشغيلة منتهية، نقل وتسوية ومنع السالب، إعادة طلب POS/دفعاته وبصمة الطلب، استهلاك مواد الخدمة من الموعد وQueue مرة واحدة، نطاق الطبيب، وإعادة حركة مخزون متزامنة مرة واحدة.
- `npm run lint` — ناجح.
- `npm run build` و`npm run pages:build` — ناجحان.

هذه النتائج محلية فقط. لم تُطبق migrations `0012–0015` على الإنتاج، ولم يُنشر فرع الميزة، ولم تُستخدم بيانات إنتاجية للاختبار.

## خطوات المتابعة

1. استكمال تدقيق API/الأدوار/الموارد التابعة، بما في ذلك ملفات المرضى، واختبار preview مرتبط بقاعدة staging منفصلة.
2. مراجعة migration `0012–0015` وخطة الإطلاق والبيانات قبل أي طلب دمج/نشر؛ لا تحديث لـ`main` تلقائيًا.
3. إبقاء EMR والوصفات الذكية والتداخلات الدوائية وبوابة العميل وGate Check-in والتقويم الموسع والمالية وسياسات الاحتفاظ ضمن الخطة، وطلب قرار المالك عندما تتطلب قاعدة طبية أو محاسبية أو خصوصية اختيارًا.
4. إبقاء بوابات الدفع الآلية والنسخ الطويل إلى R2 مؤجلتين حسب قرار المالك.
